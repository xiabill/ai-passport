# 远程 OTA 方案

这份文档记录如何让设备脱离 USB 线升级固件。目前**尚未实现**，写在这里是为了将来动手时不必重新调研。

## 现在已经能做什么

设备出厂时在 `0x700000` 预装了永久 Recovery，按住上键 5 秒进入，它对外提供 BLE 服务，FoloToy 小程序通过它安装固件。详见 [BLE 与 Recovery 兼容性](ble-recovery-compatibility.md)。

**所以不接线刷固件这件事今天就能做**，代价是每次都要手动进 Recovery 并依赖小程序。下面的方案要解决的是"在 Bridge 里点一下就升级"。

## 空间够不够

```
factory   0x010000 ~ 0x310000   3 MB     出厂槽，必须原样保留
          0x310000 ~ 0x356000   280 KB   空隙
cardid    0x356000 ~ 0x35A000   16 KB    设备身份，受保护
          0x35A000 ~ 0x700000   3.65 MB  可用
recovery  0x700000 ~ 0x800000   1 MB     永久 Recovery，必须原样保留
```

发布门禁的校验器允许衍生项目在 cardid 之后添加分区，只要 factory、cardid、recovery 三者的位置和大小分毫不动，且合并镜像在受保护区域只有 `0xFF` 填充。加 OTA 分区因此是合规的。

## 分区规划

在 `partitions.csv` 末尾追加，前五行一个字都不改：

```
otadata,  data, ota,     0x35A000, 0x2000,
ota_0,    app,  ota_0,   0x360000, 0x1A0000,
ota_1,    app,  ota_1,   0x500000, 0x1A0000,
```

结束于 `0x6A0000`，距 recovery 起点还有 384 KB 余量。

单个 app 分区上限因此是 1.66 MB。当前固件 1.2 MB，余量约 460 KB —— 值得在 CI 里加一条容量检查，避免某次改动悄悄撑破。

factory 保留 3 MB 不用于 OTA，作为最终兜底：即使两个 OTA 槽都写坏，设备仍能从出厂固件启动。ESP-IDF 的应用镜像与地址无关，同一个 `.bin` 放进任何 app 分区都能运行，所以发布产物不需要为 OTA 单独构建。

## 传输通道

复用现有的 BLE 连接，在自定义服务里新增一个只写特征接收数据块，配合 `esp_ota_begin` / `esp_ota_write` / `esp_ota_end`，校验通过后 `esp_ota_set_boot_partition` 并重启。

按当前链路的实测吞吐，1.2 MB 固件大约需要 1~2 分钟。升级期间应当拒绝录音，并在设备屏幕上显示进度。

## 工作量与风险

| 项目 | 估计 |
| --- | --- |
| 固件：分区表、OTA 服务、屏幕进度 | ~250 行 |
| Bridge：选择固件、分块推送、进度与失败处理 | ~200 行 |
| 可选：自动比对 GitHub Release 最新版 | ~150 行 |

**绕不开的前提**：分区表本身无法通过 OTA 更换，必须先用 USB 刷一次带新分区表的固件。之后才能永久摆脱线缆。

风险可控：写入失败或校验不通过时不会切换启动分区，设备继续运行原固件；即便两个 OTA 槽都损坏，factory 与 Recovery 仍是两层兜底。

## 实施顺序

1. 追加三个分区，跑 `./tools/validate.sh --firmware` 确认门禁仍然通过
2. USB 刷入一次，确认设备从 factory 正常启动、分区表已更新
3. 固件端实现 OTA 服务，先用 Bridge 推送一个与当前完全相同的镜像验证链路
4. 推送一个改了版本号的镜像，确认重启后运行的是新版本
5. 故意中断传输，确认设备回退到原分区且能继续工作
